description: 当你遇到 bug 或意外行为时使用。在修改任何代码之前先诊断根本原因，防止猜测性修复的恶性循环。
---

帮助非技术用户按结构化流程诊断并修复 bug，防止猜测性修复的恶性循环。

要求：
- 用户不懂代码。所有解释必须使用大白话，不用技术术语。
- 没有用户明确批准，绝不修改代码。
- 连续修复不超过 3 次。如果 3 次都失败，按以下协议处理。

## 第一步 — 收集症状

请用户描述：
- 你做了什么？（哪个按钮、哪个页面、哪个操作）
- 你看到了什么？（报错信息、空白页面、数据不对、什么都没发生）
- 你期望看到什么？
- 这个功能以前正常过吗？如果是，那之后改了什么？

## 第二步 — 用大白话解释根因

调查代码库，找出可能的根本原因。然后用大白话告诉用户：
- "出现这个问题的原因是：[不用技术术语的解释]"
- "打个比方：[如果有帮助的话，用生活中的类比]"

问用户："这个解释和你看到的情况吻合吗？"等待确认。

如果用户说不吻合，重新调查。不得在诊断错误的情况下继续修复。

## 第三步 — 提出最小修复方案

- 说明会修改哪些文件（按名称，不超过 2 个文件）
- 用大白话描述改动会做什么
- 说明这次改动不会影响什么

问用户："我可以去修改吗？"等待批准。

## 第四步 — 修改并验证

- 做出已获批的改动
- 提供用户可以操作的具体验证步骤：
  - "打开 [页面/界面]"
  - "点击 [按钮] / 输入 [值]"
  - "你应该看到 [期望结果]"
  - "同时检查：[不应该受影响的其他地方]"

## 第五步 — 如果 3 次都失败

停止修改。说：
> "我已经试了 3 次，问题还是存在。这说明我可能误判了根因。我建议：
> 1. 让我用全新的视角重新分析
> 2. 或者：回退到上次保存的版本，重新开始
> 3. 或者：开一个新对话，从头描述这个问题"

请用户选择其中一个方向。
